Harness Engineering for AI-First Development

July 5, 2026 · AI Engineering · Software Engineering

Building Better Software

For decades, software engineering revolved around developers translating ideas into code by manually applying language syntax, frameworks, design patterns, and APIs. Today, AI coding agents have fundamentally changed that workflow.

Modern coding agents can generate code, refactor existing systems, write tests, perform code reviews, execute commands, and even deploy applications. As a result, the developer's primary responsibility is gradually shifting away from writing code toward designing solutions, defining architecture, and verifying correctness.

Artificial intelligence is not competing with software engineers any more than a compiler competes with programmers or Git competes with project managers. AI is another engineering tool — arguably the most capable tool ever built.

Like every engineering tool, however, it must be used correctly.

Importance of Tools

Humans are superior to all other beings because they can reason, discover, innovate, invent tools, and use them.

Imagine asking a person to race a cheetah. The result is obvious.

Now give that same person a Ferrari. The outcome changes completely.

The Ferrari did not replace the driver's intelligence. It amplified it.

AI coding agents work the same way. They don't replace engineering judgment — they amplify it.

An experienced engineer still decides:

  • what should be built
  • why it should be built
  • how success is measured
  • what trade-offs are acceptable
  • what architectural constraints must never be violated

The coding agent accelerates implementation. The human remains responsible for engineering decisions.

AI Tokens Are an Engineering Resource

Every API request sent to an AI model consumes compute.

It is tempting to think that reducing token usage should become the primary objective.

But the goal is not to make AI cheaper.

The goal is to eliminate unnecessary reasoning.

Consider two agents. The first spends thousands of tokens:

  • rediscovering the repository
  • searching irrelevant files
  • guessing coding conventions
  • implementing the wrong abstraction
  • repeatedly fixing avoidable mistakes

The second spends the same reasoning budget implementing the feature.

Both may consume similar tokens. Only one produced engineering value.

Cost is therefore an outcome, not the objective. The objective is:

Maximize verified engineering output per unit of reasoning.

That distinction is fundamental.

Why Coding Agents Waste Tokens

AI does not spend that many tokens writing code. In reality, a significant portion of its reasoning budget is often spent understanding the project.

The agent may have to determine:

  • Which framework is being used?
  • Which architectural pattern should I follow?
  • Where are repository methods located?
  • How are database migrations written?
  • Which testing framework should I use?
  • How do I build the project?
  • Which coding conventions are mandatory?

If none of this information exists inside the repository, the agent has only one option: it starts exploring. Exploration means:

  • reading files
  • searching directories
  • comparing implementations
  • making assumptions
  • revising assumptions

Every one of those steps consumes context, tool calls, and tokens.

This observation aligns with Martin Fowler's writing on harness engineering: the quality of the execution environment often matters more than switching to a larger model.

Harness Engineering

Harness engineering is the discipline of designing the environment in which coding agents operate.

The model itself may remain exactly the same. What changes is everything surrounding it:

  • repository structure
  • documentation
  • initialization
  • verification
  • state management
  • constraints
  • observability

A good harness allows the agent to spend its reasoning budget solving the engineering problem instead of discovering how the project works.

OpenAI and Anthropic have both published detailed engineering articles describing this philosophy — OpenAI's account of building an agent-first codebase with Codex and Anthropic's write-up on effective harnesses for long-running agents. Martin Fowler's article on harness engineering also provides an excellent overview of why the discipline is becoming a core part of software engineering.

The Repository Is the Agent's Brain

One principle deserves special emphasis.

If information is not inside the repository, it effectively does not exist for the agent.

Developers frequently rely on knowledge that lives only inside their heads:

  • architecture decisions
  • naming conventions
  • coding standards
  • deployment procedures
  • testing expectations

Humans can ask teammates. AI cannot.

If the repository doesn't document these rules, the agent must either guess or spend tokens discovering them. Neither outcome is desirable.

What Every AI-Friendly Repository Should Contain

Rather than maintaining one enormous instruction file, organize repository knowledge into focused documents.

AGENTS.md

The landing page for the coding agent. Keep it concise. It should answer:

  • What is this project?
  • How do I build it?
  • How do I test it?
  • Which constraints are non-negotiable?
  • Where can I find additional documentation?

Architecture Documents

Document:

  • architectural decisions
  • coding conventions
  • dependency rules
  • module responsibilities

Place documentation close to the code it describes.

Progress.md

Long-running implementations rarely finish in one session. Persist:

  • completed work
  • current progress
  • blockers
  • next actions

This prevents future sessions from rediscovering the same information.

Task Routing

Rather than forcing the agent to search the repository, document:

  • which modules are involved
  • expected files to modify
  • related documentation
  • affected tests

Reducing unnecessary exploration directly improves engineering efficiency.

Verification

Never allow an agent to decide that work is complete simply because "the code looks correct."

Document:

  • build commands
  • lint commands
  • unit tests
  • integration tests
  • end-to-end verification
  • definition of done

Completion should be determined by evidence, not confidence.

Human Planning vs. Agent Planning

Should a feature be implemented using one large prompt or many smaller prompts?

For mature production systems, prefer a hybrid approach: first perform the architectural decomposition.

For example, implementing a Forgot Password feature naturally breaks into independently verifiable steps:

  1. Database schema
  2. Repository methods
  3. Business logic
  4. Email integration
  5. User interface
  6. End-to-end verification

Instead of asking the coding agent to simultaneously design the architecture and implement it, provide the architectural roadmap and allow the agent to focus on implementation.

This reduces exploratory reasoning while keeping engineering decisions under human control.

The objective is to ensure the agent spends its reasoning budget implementing rather than guessing.

Measuring Harness Quality

One common mistake is comparing only token consumption. That produces misleading conclusions.

A better benchmark compares:

MetricWhy It Matters
Verified feature completionMeasures actual engineering output
Production readinessIndicates deployable quality
Repository convention complianceShows architectural consistency
Number of follow-up promptsMeasures implementation completeness
Tool callsIndicates exploration efficiency
Files exploredMeasures discovery cost
Total tokensMeasures reasoning budget
Total execution costMeasures economic efficiency

Sometimes the harnessed implementation may even consume more tokens during the first prompt. That does not automatically mean it is less efficient.

If the non-harnessed implementation requires ten follow-up prompts while the harnessed implementation succeeds after one or two, the total engineering cost strongly favors the harnessed repository.

Measure the entire implementation lifecycle — not individual prompts.

Harnesses Evolve

A harness is not documentation that you write once. It evolves with the repository.

Every architectural decision… every new convention… every important review comment… every recurring mistake… should gradually become part of the harness.

Otherwise the repository accumulates a different kind of technical debt:

AI debt.

Over time, outdated instructions, inconsistent documentation, and missing verification cause coding agents to spend increasingly more effort rediscovering information that should already be explicit.

Maintaining the harness becomes as important as maintaining the code itself.

Final Thoughts

AI is about allowing engineers to spend less time translating ideas into syntax and more time solving problems.

The best engineering teams will not necessarily be those with the largest models or the biggest budgets.

They will be the teams that design repositories where AI agents can operate predictably, efficiently, and reliably.
