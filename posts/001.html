Undocumented Enhancements in PostgreSQL 16: GIN Index Behavior Under RLS

January 25, 2026 · PostgreSQL · Indexing

While analyzing database health warnings reported by pg_firstaid, I encountered an interesting planner behavior involving GIN indexes, Row Level Security (RLS), and full-text search. What initially appeared as an unused index turned out to be a clear example of undocumented planner improvements introduced in PostgreSQL 16.

However, deeper investigation revealed a more nuanced reality — one that depends heavily on PostgreSQL version, planner behavior, and Row Level Security (RLS). An index that is unused in PostgreSQL 15 can become critical in PostgreSQL 16, without any schema changes.

Background: pg_firstaid Warning

pg_firstaid flagged the following warning:

CRITICAL — Unused Large Index

The index in question was a GIN index created on a tsvector column used for full-text search. According to pg_firstaid, the index was consuming disk space while never being selected by the query planner.

The tool also links to the official PostgreSQL documentation on index removal (DROP INDEX). From a PostgreSQL 15 perspective, this assessment was technically correct. However, blindly following the recommendation would have been the wrong decision given the system’s upgrade path.

PostgreSQL 15: Why the GIN Index Is Ignored

Under PostgreSQL 15, the query planner behaves conservatively when full-text search is combined with Row Level Security (RLS).

In practice, this resulted in the following behavior:

  • The planner used a primary key or B-tree index only for tenant filtering
  • Full-text search (@@ to_tsquery(...)) was applied row-by-row
  • The GIN index on the tsvector column was completely ignored
  • Large datasets resulted in hundreds of thousands of rows being scanned
  • Execution times ranged from several seconds per query

From the planner’s point of view, the GIN index was not considered selective enough under RLS. This explains why pg_firstaid correctly reported the index as unused.

Composite GIN Indexes: PostgreSQL 15 vs PostgreSQL 16

PostgreSQL 15

While exploring workarounds, I attempted to create a composite GIN index that included a non-text column (such as a tenant identifier): 

CREATE INDEX ... USING gin (tenant_id, search_vector);

This fails in PostgreSQL 15. GIN requires every indexed column to have a valid operator class, and scalar types such as bigint do not have a default GIN operator class. This behavior is documented and expected.

PostgreSQL 16

Surprisingly, the same index definition succeeds in PostgreSQL 16.

More importantly, PostgreSQL 16 does not actually require a composite GIN index to perform well. A simple GIN index on the tsvector column alone is sufficient, even when RLS is enabled.

Query Plan Comparison: PostgreSQL 15 vs PostgreSQL 16

PostgreSQL 15

  • GIN index not used
  • Tenant filtering applied first
  • Full-text search evaluated row-by-row
  • Large number of rows scanned
  • Execution time measured in seconds

This fully explains why pg_firstaid categorised the index as unused.

PostgreSQL 16

  • GIN index selected by the planner
  • Bitmap index scan on the GIN index
  • RLS filtering applied efficiently
  • Very small number of heap pages accessed
  • Execution time measured in milliseconds

Under PostgreSQL 16, pg_firstaid no longer reports the index as unused.

Documentation vs Observed Behavior

PostgreSQL 16 release notes mention improvements in planner selectivity estimation, GIN index costing, and overall planning accuracy.

However, there is no explicit documentation stating that PostgreSQL 16 uses GIN indexes more effectively under Row Level Security.

This conclusion is based entirely on repeatable, side-by-side testing of execution plans and performance across PostgreSQL 15 and PostgreSQL 16.

Key Takeaways

  • pg_firstaid correctly flags unused GIN indexes on PostgreSQL 15
  • Dropping such indexes without considering upgrade plans can be risky
  • PostgreSQL 15 does not reliably use GIN indexes under RLS
  • PostgreSQL 16 dramatically improves this behavior without schema changes
  • Some planner improvements are empirical, not explicitly documented

Final Thoughts

This investigation reinforced an important lesson: index analysis tools are correct within the context of the current planner, but upgrade-aware decisions require deeper analysis.

In this case, retaining an “unused” index avoided unnecessary rework and unlocked significant performance gains after upgrading to PostgreSQL 16.

If your workload relies heavily on full-text search with Row Level Security, PostgreSQL 16 is a meaningful step forward.
